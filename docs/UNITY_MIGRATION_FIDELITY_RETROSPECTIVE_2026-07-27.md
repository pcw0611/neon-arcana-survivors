# Unity 마이그레이션 유사도 이탈 회고와 재발 방지 기준

> 작성일: 2026-07-27
>
> 대상: Unity 마이그레이션 1·2단계
>
> 성격: 비난을 위한 문서가 아니라 원인, 책임, 복구 기준을 고정하는 사후 회고
>
> 관련 문서: [`UNITY_MIGRATION_PHASE1.md`](UNITY_MIGRATION_PHASE1.md), [`UNITY_MIGRATION_PHASE2.md`](UNITY_MIGRATION_PHASE2.md)

## 1. 결론

현재 Unity 프로젝트는 컴파일, 자동 전투, 대량 적 처리, 강화·유물·보스·전직 시스템 같은
**기술 프로토타입 기준**에서는 2단계 구현을 마쳤다.

그러나 사용자가 기대한 것은 웹 게임의 규칙과 경험을 Unity로 보존하는 마이그레이션이었고,
Unity 결과물은 이 기준을 충족하지 못했다.

- 목표 유사도: 체감 80~90% 이상
- 현재 사용자 평가: 약 20~30%
- 검토 결론: 사용자 평가는 타당하다.
- 현재 상태 표기: **기술 구현 완료 / 마이그레이션 유사도 미승인**

문제의 핵심은 Unity의 한계나 원본 그래픽의 CSS·Canvas 구현 방식이 아니다.
목표를 기능 목록으로 좁혀 해석하고, 원본 플레이 경험을 완료 조건에 포함하지 않은 진행 방식이다.

## 2. 무엇이 달라졌는가

### 2.1 조작 규칙

웹 버전의 성좌탄은 자동 공격이다.

`public/game-v4.js`의 `fire()`는 발사할 때마다 `findTarget()`으로 대상을 고르고,
선택된 적을 향해 투사체를 발사한다.

마우스 방향은 주로 광검 방향과 캐릭터가 바라보는 방향에 사용된다.
터치 입력도 하나의 드래그 이동 입력이며 공격용 우측 패드가 없다.

Unity 버전에는 다음 규칙이 추가됐다.

- 왼쪽 이동 패드
- 오른쪽 조준 패드
- 마우스 조준
- 조준 입력이 있으면 성좌탄도 해당 방향으로 발사

이는 입력 장치를 Unity로 변환한 것이 아니라 게임 규칙을 변경한 것이다.
사용자 승인 없이 추가하면 안 되는 변경이었다.

### 2.2 화면과 사용자 경험

웹 버전에는 다음 요소가 하나의 흐름으로 연결돼 있다.

- 타이틀 화면과 캐릭터 일러스트
- 언어 선택
- 글로벌 랭킹 패널
- 사이버 도시 배경
- 캐릭터 애니메이션
- 미니맵과 적 수 표시
- 경험치, 체력, 점수, 시간 HUD
- 레벨업 일시 정지와 3개 카드 선택
- 유물 선택·교체
- 보스와 전투 효과
- 화면 흔들림, 타격, 링, 파티클 등 전투 연출

Unity 버전은 일부 원본 PNG를 가져왔지만 다음 부분이 크게 단순화됐다.

- 타이틀과 랭킹 흐름 생략
- 코드 생성형 HUD
- 임시 색상 사각형으로 만든 패드와 일부 투사체
- 프리팹과 Animator 부재
- 웹판과 다른 정보 배치와 크기
- 제한적인 전환·타격·선택 연출
- `PHASE 2 · CONTENT SHOWCASE` 같은 개발 확인용 표시

결과적으로 Unity판은 웹판보다 고급 렌더링 엔진을 사용하면서도
사용자가 보는 완성도는 낮아졌다.

### 2.3 프로젝트 구조

현재 `Assets` 아래에는 전용 `.prefab` 파일이 없다.

플레이어, 적, 투사체, HUD, 버튼, 패드와 다수의 런타임 오브젝트를
`new GameObject()`와 정적 `Create()` 함수로 생성한다.

이 방식은 초기 자동 검증에는 편리하지만 다음 문제가 있다.

- 에디터에서 시각적으로 수정하기 어렵다.
- 아티스트와 디자이너가 값을 조정하기 어렵다.
- 오브젝트별 애니메이션과 VFX 구성을 확인하기 어렵다.
- 모바일 해상도별 UI 튜닝이 코드 변경에 종속된다.
- 원본 화면과 나란히 비교하며 수정하는 속도가 느리다.

1단계 문서에는 안정화된 오브젝트를 2단계에서 프리팹과 데이터로 옮기겠다고 기록했다.
실제 2단계에서는 이 약속을 이행하지 않고 다시 다음 단계로 미뤘다.

## 3. 왜 이런 결과가 나왔는가

한 사람의 단일 실수보다 여러 조건이 같은 방향으로 겹친 결과다.

### 3.1 주문의 모호성

초기 주문은 “Unity 마이그레이션”이었고 이후 “코어 프로토타입부터”라는 지시가 추가됐다.

“코어 프로토타입”은 다음 두 의미로 해석될 수 있다.

1. 원작의 핵심 플레이 경험을 최소 범위로 정확히 재현
2. Unity에서 기술적으로 돌아가는 게임 루프를 빠르게 검증

사용자는 첫 번째 의미를 기대했지만 구현은 두 번째 의미로 진행됐다.

또한 초기에 다음 기준이 명시적으로 숫자나 금지 규칙으로 고정되지는 않았다.

- 목표 체감 유사도 80~90%
- 원작 조작을 임의로 변경하지 말 것
- 성좌탄은 자동 표적 공격을 유지할 것
- 프리팹을 어느 단계까지 만들 것
- 임시 그래픽을 허용하는 범위
- 화면별 승인 절차

이 모호성은 오해가 시작될 여지를 만들었다.

다만 이것이 구현자의 책임을 없애지는 않는다.
일반적으로 “마이그레이션”은 별도 승인이 없는 한 동작과 사용자 경험을 보존하는 작업이다.
모호한 부분이 발견되면 구현자가 질문하고 가정을 문서화했어야 한다.

### 3.2 원본을 플레이하기 전에 구조를 결정

구현자는 초기에 저장소 문서와 코드 중심으로 원본을 분석했다.
라이브 웹 버전을 충분히 플레이하고 다음 항목을 기록하는 절차가 먼저 오지 않았다.

- 첫 진입부터 한 판 종료까지의 전체 흐름
- 자동 공격과 수동 조작의 정확한 경계
- 레벨업과 유물 선택의 화면 전환
- 캐릭터별 공격 방향 규칙
- 보스 등장과 경고 연출
- 데스크톱과 터치 입력 차이

코드에 있는 기능의 존재는 파악했지만, 플레이 감각과 우선순위를 놓쳤다.

### 3.3 기술 검증을 제품 유사도보다 우선

다음 목표가 사실상 최상위 완료 조건으로 사용됐다.

- Unity 배치 모드에서 자동 설정 가능
- 컴파일 성공
- Play Mode 스모크 성공
- Windows 빌드 성공
- Android APK 생성
- 적 수와 시스템 수가 목표치에 도달

이 검증들은 필요하지만 마이그레이션의 충분조건은 아니다.

“실행된다”와 “원작처럼 실행된다”를 구분하지 않은 것이 핵심 오류다.

### 3.4 기능 수 중심의 단계 분해

2단계 진행은 다음 숫자를 채우는 방식으로 관리됐다.

- 강화 34종
- 유물 21종
- 적 아키타입 6종
- 보스 4종
- 전직 5종

목록의 존재 여부는 빠르게 측정할 수 있지만 다음 항목은 측정하지 않았다.

- 각 기능이 원본과 같은 조건에 발동하는가
- 같은 대상을 선택하는가
- 같은 방향과 타이밍으로 공격하는가
- 같은 순서로 UI가 나타나는가
- 같은 수준의 시각 피드백을 제공하는가

따라서 콘텐츠 양은 늘었지만 유사도는 비례해 오르지 않았다.

### 3.5 승인받지 않은 설계 개선

오른쪽 공격 패드는 모바일 편의를 위한 개선이라고 가정했다.
그러나 마이그레이션 단계에서 개선은 자동으로 허용되지 않는다.

원본과 다른 설계를 넣으려면 최소한 다음 절차가 필요했다.

1. 원본 동작을 먼저 동일하게 구현
2. 변경 이유와 장단점 제시
3. 사용자의 명시적 승인
4. 별도 옵션이나 실험 브랜치로 구현

이 절차 없이 들어간 우측 패드는 기능 추가가 아니라 원본 이탈이다.

### 3.6 임시 구조가 영구 구조로 굳음

1단계의 런타임 생성 구조는 빠른 검증을 위한 임시 선택이었다.
하지만 2단계에서 콘텐츠를 추가할 때 같은 구조 위에 계속 기능을 쌓았다.

프리팹 전환은 기능 구현을 잠시 늦추는 작업처럼 보였고,
측정하기 쉬운 콘텐츠 수를 먼저 늘리면서 계속 뒤로 밀렸다.

이는 전형적인 프로토타입 부채의 고착이다.

### 3.7 완료 보고 방식

문서와 보고에서는 “2단계 완료”가 크게 표시됐다.
제한 사항에는 프리팹, 애니메이션, 오디오가 없다고 적었지만
다음 두 상태가 분리되지 않았다.

- 기술 시스템 구현 상태
- 원작 마이그레이션 승인 상태

사용자가 스크린샷을 볼 수 있었더라도,
완료 보고가 기술 성공을 중심으로 구성돼 있었기 때문에
유사도 검토를 별도 승인 단계로 인식하기 어려웠다.

## 4. 사용자 주문에서 개선할 수 있었던 점

이 절은 사용자에게 책임을 전가하기 위한 내용이 아니다.
앞으로 사람과 에이전트가 같은 의미로 작업을 시작하기 위한 주문 개선안이다.

### 4.1 잘못됐다고 단정할 수 없는 부분

“Unity로 마이그레이션해 달라”는 주문 자체는 정상적이다.
마이그레이션은 일반적으로 원본의 동작과 경험을 보존한다는 뜻이므로,
사용자가 모든 보존 규칙을 일일이 나열해야만 하는 것은 아니다.

“코어 프로토타입부터”라는 주문도
단계적으로 위험을 줄이기 위한 합리적인 요청이다.

### 4.2 오해를 더 줄일 수 있었던 부분

다음 조건을 초기에 명시했다면 해석 오류를 더 빨리 차단할 수 있었다.

- 프로토타입이어도 게임 규칙과 조작은 원작과 동일해야 한다.
- 그래픽은 임시일 수 있지만 화면 구성은 원작을 기준으로 한다.
- 독자적인 기능 추가나 UX 변경은 사전 승인 대상이다.
- 목표 체감 유사도는 최소 80%다.
- 1단계 종료 전에 웹판과 Unity판을 나란히 비교한다.
- 프리팹과 에디터 편집 구조를 필수 산출물로 포함한다.

그러나 이 조건이 없었다고 해서 임의 변경이 자동으로 허용되는 것은 아니다.
불명확한 지점은 구현자가 확인해야 한다.

## 5. 책임 구분

| 주체 | 책임 |
|---|---|
| 사용자 | 목표 유사도, 절대 바꾸면 안 되는 경험, 허용 가능한 개선 범위를 가능한 한 명시 |
| 구현자 | 마이그레이션을 기본적으로 보존 작업으로 해석하고, 변경 전 질문 |
| 구현자 | 라이브 버전을 직접 플레이하고 행동 명세와 기준 화면 작성 |
| 구현자 | 기술 완료와 유사도 승인을 분리해 보고 |
| 공동 | 각 단계 시작 전에 완료 기준과 비교 화면 합의 |
| 공동 | 단계 종료 시 빌드나 영상으로 직접 비교하고 다음 단계 진입 승인 |

현재 이탈의 직접적인 구현 책임은 Codex에 있다.
사용자의 주문에는 해석 여지가 있었지만,
구현자가 그 여지를 확인하지 않고 독자적인 조작과 구조를 선택했다.

## 6. 재발 방지 절차

앞으로 마이그레이션 작업은 다음 순서를 강제한다.

### 6.1 0단계: 원본 기준선 확보

코드를 수정하기 전에 다음 자료를 만든다.

- 라이브 버전 10분 이상 직접 플레이
- 타이틀, 전투, 레벨업, 유물, 보스, 게임 오버 기준 화면
- 데스크톱과 모바일 입력표
- 무기별 표적 선택과 발사 규칙
- 화면 전환 순서
- 원본의 의도적인 불편함과 개선 후보 분리

기준선이 승인되기 전에는 Unity 구조를 확정하지 않는다.

### 6.2 마이그레이션 계약

각 단계 문서 첫 부분에 다음 표를 둔다.

| 항목 | 내용 |
|---|---|
| 원본 기준 | 라이브 URL, 커밋 SHA, 기준 캡처 |
| 보존 대상 | 게임 규칙, 입력, UI 흐름, 수치, 연출 |
| 변경 허용 | 사용자가 승인한 항목만 |
| 임시 허용 | 대체 가능한 아트와 그 만료 단계 |
| 목표 유사도 | 전체 및 영역별 점수 |
| 승인 방법 | 비교 영상, 스크린샷, 플레이 빌드 |

### 6.3 변경 통제

원본과 다른 동작을 발견하거나 제안할 때는 다음 형식으로 기록한다.

```text
변경 후보:
원본 동작:
제안 동작:
변경 이유:
장점:
손실:
사용자 승인: 대기 / 승인 / 거절
```

`사용자 승인: 대기`인 변경은 기본 브랜치에 구현하지 않는다.

### 6.4 유사도 점수표

다음 가중치를 기본값으로 사용한다.

| 영역 | 가중치 | 평가 예시 |
|---|---:|---|
| 게임 규칙 | 30 | 표적, 발사, 피해, 성장, 보스 조건 |
| 조작 | 20 | 이동, 자동 공격, 마우스·터치 역할 |
| 화면과 UX 흐름 | 20 | 시작, HUD, 선택, 결과 화면 |
| 시각·연출 | 20 | 캐릭터, 적, VFX, 색, 전환, 카메라 |
| 프로젝트 구조 | 10 | 프리팹, 데이터, 에디터 편집성 |
| 합계 | 100 | 80점 이상이 기본 통과선 |

추가 규칙:

- 전체 80점 이상
- 게임 규칙과 조작은 각각 85점 이상
- 사용자 미승인 동작 변경은 1건이라도 있으면 실패
- 임시 그래픽은 문서에 만료 단계를 기록

### 6.5 세 종류의 검증

기존 기술 검증만으로 완료 처리하지 않는다.

1. 기술 검증
   - 컴파일, 테스트, 빌드, 성능
2. 행동 동등성 검증
   - 같은 입력과 조건에서 같은 표적·공격·선택·결과
3. 시각 회귀 검증
   - 동일 해상도의 원본·Unity 스크린샷 또는 영상 비교

세 영역이 모두 통과해야 “마이그레이션 단계 완료”라고 표기한다.

### 6.6 프리팹 기준

다음 요소는 런타임에서 형태 전체를 코드로 만들지 않는다.

- 플레이어
- 일반 적과 아키타입
- 보스
- 플레이어·적 투사체
- 경험치와 드롭
- HUD
- 레벨업·유물·보스 선택 화면
- 모바일 입력 UI
- 주요 VFX

런타임 생성이 필요한 것은 풀에서 꺼낼 프리팹 인스턴스다.
코드는 동작을 담당하고, 시각 구성과 직렬화 참조는 프리팹에서 편집할 수 있어야 한다.

### 6.7 단계 종료 게이트

각 단계 종료 전 다음 질문에 모두 `예`라고 답해야 한다.

- 원본을 다시 플레이하고 비교했는가?
- 원본과 다른 동작을 모두 목록화했는가?
- 미승인 변경이 없는가?
- 기준 화면을 같은 조건에서 캡처했는가?
- 기술 완료와 유사도 점수를 따로 보고했는가?
- 사용자가 비교 결과를 보고 다음 단계 진입을 승인했는가?

하나라도 `아니오`면 다음 단계로 넘어가지 않는다.

## 7. 현재 프로젝트에 즉시 적용할 상태 정정

기존 “2단계 완료” 표시는 다음처럼 해석을 정정한다.

| 구분 | 상태 |
|---|---|
| 1단계 Unity 기술 프로토타입 | 완료 |
| 2단계 콘텐츠 시스템 기술 구현 | 완료 |
| 웹판 행동 동등성 | 미승인 |
| 입력 유사도 | 실패 |
| 시각·UX 유사도 | 실패 |
| 프리팹 전환 | 미완료 |
| 전체 마이그레이션 2단계 | 유사도 보정 필요 |

사용자가 새로 정의할 3단계는 유사도 복구를 중심으로 구성한다.
기존에 3단계로 예정했던 출시·백엔드·장시간 QA 작업은 4단계로 이동한다.

새 3단계의 정확한 범위와 순서는 사용자의 다음 지시를 기준으로 확정하며,
이 문서에서 임의로 기능 목록을 확정하지 않는다.

## 8. 권장 주문 템플릿

앞으로 유사한 작업을 시작할 때 다음 문구를 기본 계약으로 사용할 수 있다.

```text
이 작업은 재해석이나 리메이크가 아니라 마이그레이션이다.
별도 승인 없이 게임 규칙, 조작, 화면 흐름을 변경하지 않는다.

먼저 원본을 직접 플레이하고 행동·화면 기준표를 작성해 승인받아라.
단계별 체감 유사도 목표는 최소 80%이며,
게임 규칙과 조작은 85% 이상이어야 한다.

기술 테스트 통과와 마이그레이션 완료를 별도로 보고하라.
원본과 다른 개선안은 구현 전에 장단점을 제시하고 승인을 받아라.
플레이어, 적, 투사체, HUD, 선택 화면은 Unity 프리팹으로 편집 가능해야 한다.
각 단계 종료 시 원본과 Unity의 동일 장면 비교 자료를 제출하라.
```

이 템플릿은 사용자의 부담을 늘리기 위한 것이 아니다.
구현자가 임의 해석을 하지 못하게 기준을 고정하는 안전장치다.

## 9. 최종 교훈

- 프로토타입은 낮은 완성도를 허용할 수 있지만 다른 게임 규칙을 허용하지는 않는다.
- 마이그레이션은 기능 이름이 아니라 행동과 경험을 옮기는 작업이다.
- 자동 테스트는 원작 유사도를 증명하지 않는다.
- 개선처럼 보이는 변경도 승인 없이는 회귀다.
- 임시 런타임 생성 구조에는 명확한 종료 단계가 필요하다.
- 완료라는 단어는 기술 구현과 사용자 승인에 나눠 사용해야 한다.
- 사용자의 다음 지시를 기다리기 전에 구현자가 모호성을 먼저 드러내야 한다.

이번 회고의 목적은 책임을 나누어 희석하는 것이 아니다.
주문의 모호성, 구현자의 잘못된 해석, 승인 절차의 부재를 각각 분리해
같은 문제가 다시 발생할 경로를 닫는 것이다.
